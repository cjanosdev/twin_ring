#[actix_web::main]

- This is a macro attribute provided by Actix.
- It transforms your main into an async entry point, setting up a Tokio runtime under the hood
- Without this, Rust doesn't let you write async fn main directly.


async fn main() -> std::io::Result<()>
- defines the programs entry point
- async fn returns a Future (so Actix can .await everything).
Return type std::io::Result<()>
- Result <T, E> is Rust's success/failure type
- Here, success = (), the empty tuple (no real  value).
- Failure = std::io::Error

So main runs asynchronously and may return an I/O error.

In Rust, errors are not exceptions - they're explicit values

enum Result<T, E> {
    OK(T), // success holds a value of type T
    Err(E), // failure,holds an error of type E
}

Result<T, E> is a generic enum

Exmaple: Result<String, io::Error> means "either a String (success) or an I/O error (failure)."


fn might_fail(divisor: i32) -> Result<i32, String> {
    if divisor == 0 {
        Err("Division by zero".into())
    } else {
        Ok(10 / divisor)
    }
}

fn main() {
    match might_fail(0) {
        Ok(val) => println!("Got value: {}", val),
        Err(e)  => println!("Error: {}", e),
    }
}

The ? operator in Rust is error propogation

fn read_file() -> Result<String, io::Error> {
    let mut f = File::open("foo.txt");
    if f.is_err() {
        return Err(f.unwrap_err());
    }
    let mut file = f.unwrap();

    let mut s = String::new();
    let res = file.read_to_string(&mut s);
    if res.is_err() {
        return Err(res.unwrap_err());
    }
    Ok(s)
}

unwrap()

.unwrap() means "If this is Ok, give me the value inside. IF it's Err, crash the program (panic)."

example:

let x = Some(5);
println!("{}", x.unwrap()); //prints 5

let y: Option<i32> = None;
println!("{}", y.unwrap()); // panic at runtime

unwrap = take the inside value or blow up


In Rust, unwrap() is a method available on Option and Result enums. Its purpose is to extract the contained value from a Some variant of an Option or an Ok variant of a Result.
How unwrap() works:
For Option<T>: If the Option is Some(value), unwrap() returns value. If the Option is None, unwrap() causes the program to panic!.
For Result<T, E>: If the Result is Ok(value), unwrap() returns value. If the Result is Err(error), unwrap() causes the program to panic!.



The ? operator is like a safe version of unwrap that propagates errors

if the result is Ok(val) it unwraps and gives you val
if the result is Err(e) it returs early from the current function with that error

example:
fn read_file() -> Result<String, std::io::Error> {
    let mut s = String::new();
    let mut f = File::open("foo.txt")?;  // if Err -> return Err
    f.read_to_string(&mut s)?;           // if Err -> return Err
    Ok(s)
}


so back to:
with ? operator

fn read_file() -> Result<String, io::Error> {
    let mut s = String::new();
    File::open("foo.txt")?.read_to_string(&mut s)?;
    Ok(s)
}


So why don’t we need f.is_err() checks?

Because ? does that implicitly. It’s sugar for:

match File::open("foo.txt") {
    Ok(val) => val,
    Err(e)  => return Err(e),
}

In C, this is handled by varargs (printf), but varargs are unsafe — the compiler can’t check types, so mismatches cause runtime bugs. Rust doesn’t allow unsafe implicit varargs like C.


println! is a macro (not a function) because:

Rust doesn’t support unsafe C-style varargs.

Macros can validate arguments at compile time.

It’s really shorthand for a bunch of lower-level code.

So it’s not an “odd choice” — it’s a deliberate tradeoff:

Safety + flexibility (macros) over simplicity but unsafe (functions).

fn bind<A: ToSocketAddrs>(self, addr: A) -> std::io::Result<Self>
1. Function name and generics

fn bind<A: ToSocketAddrs>
fn bind = function named bind.

<A: ToSocketAddrs> = generic type parameter:

A is a placeholder type.

It must implement the trait ToSocketAddrs.

So this means: “bind takes an argument of some type A, as long as A implements the ToSocketAddrs trait.”


(self, addr: A)
In Rust, self is like this in other languages.

It means this is a method defined on a type (here, HttpServer).

self by value means it takes ownership of the server instance.

So .bind(...) consumes the old HttpServer and returns a new one.

That’s why you can chain methods (.bind(...).run()).


Other forms:

&self → borrow immutably.

&mut self → borrow mutably.

self → take ownership.


-> std::io::Result<Self>
Return type is std::io::Result<Self>.

Result<T, E> = success/failure type (we discussed).

Here, T = Self (the same type the method is defined on, i.e., HttpServer).

E = std::io::Error (because Result defaults to Result<T, std::io::Error> when you use std::io::Result).
